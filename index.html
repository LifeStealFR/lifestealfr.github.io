Guide 1 · Bots Discord · Production · ~520 mots

Architecture et déploiement d'un bot Discord moderne en production

Un bot Discord qui dépasse le stade du prototype doit être pensé comme un service distribué : connexion résiliente à la passerelle Discord, séparation stricte entre la logique métier et la couche transport, et supervision du cycle de vie des processus. Avec Discord.js v14, la première décision structurante concerne les Gateway Intents : ne souscrivez qu'aux intents strictement nécessaires (par exemple Guilds, GuildMembers et GuildMessages si la modération l'exige) afin de réduire la surface mémoire et de rester conforme au principe du moindre privilège. Les intents privilégiés se déclarent explicitement dans le portail développeur et doivent être justifiés fonctionnellement.

Structurer le code : commandes, événements et services

Organisez le projet en trois couches. La couche transport (client Discord.js, enregistrement des slash commands, gestionnaires d'événements) ne contient aucune règle métier. La couche services expose des fonctions pures et testables (modération, planification, persistance). La couche infrastructure regroupe la configuration, les clients base de données et les files d'attente. Les commandes slash sont enregistrées via l'API REST de Discord au déploiement, jamais à chaque démarrage, afin d'éviter les limites de taux. Stockez les identifiants d'application et les tokens exclusivement dans des variables d'environnement injectées au runtime.

Sharding et cycle de vie des processus

Au-delà d'environ 2 500 guildes, Discord impose le sharding : la charge de la passerelle est répartie sur plusieurs processus (shards) coordonnés par un gestionnaire. Prévoyez dès le départ un ShardingManager qui surveille les redémarrages, propage les arrêts gracieux (SIGTERM) et répercute les variables d'environnement à chaque shard. Chaque shard expose une sonde de santé locale (statut de connexion, latence heartbeat, nombre de guildes) remontée vers le superviseur. Un arrêt gracieux ferme les connexions base de données, termine les tâches planifiées en cours et confirme la fin du traitement avant de quitter : c'est ce qui évite les doubles réponses et les états corrompus lors des mises à jour.

Conteneurisation et PM2 : une stratégie de déploiement reproductible

En production, figez les dépendances avec un package-lock.json versionné et construisez une image Docker minimale (base Node.js LTS slim, utilisateur non-root, healthcheck HTTP). Pour les hôtes Linux classiques sans orchestrateur, PM2 reste un gestionnaire de processus robuste : redémarrage automatique, mode cluster pour les workers stateless, rotation des journaux et démarrage au boot via pm2 startup. La configuration ci-dessous illustre un déploiement canonique avec variables d'environnement séparées par environnement :

// ecosystem.config.js — déploiement PM2 du bot et de son shard manager
module.exports = {
  apps: [{
    name: "kurotsuki-shards",
    script: "./src/shard-manager.js",
    instances: 1,
    exec_mode: "fork",
    watch: false,
    max_memory_restart: "512M",
    restart_delay: 5000,
    exp_backoff_restart_delay: 100,
    env_production: {
      NODE_ENV: "production",
      DISCORD_TOKEN: process.env.DISCORD_TOKEN,
      DATABASE_URL: process.env.DATABASE_URL,
      LOG_LEVEL: "info"
    }
  }]
};
# Dockerfile minimal — image reproductible, utilisateur non-root
FROM node:20-bookworm-slim
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY src ./src
RUN useradd -r bot && chown -R bot:bot /app
USER bot
HEALTHCHECK --interval=30s --timeout=5s CMD node ./src/healthcheck.js
CMD ["node", "./src/shard-manager.js"]
Checklist de mise en production : intents minimaux déclarés, commandesslash enregistrées au déploiement, secrets hors du dépôt, healthcheck exposé, journaux centralisés avec identifiant de shard, sauvegardes de la base avant chaque migration, et procédure de rollback testée.

Tests, charge et exploitation courante

Avant chaque mise en production, exécutez les tests unitaires des services, un test de contrat sur l'enregistrement des commandes et un test de charge modéré sur les routes les plus sollicitées (statuts, classements, modération). En exploitation, surveillez la latence du heartbeat de la passerelle, la taille des files d'événements et la consommation mémoire par shard : une dérive lente signale généralement une fuite (écouteurs non retirés, temporisateurs oubliés) plutôt qu'un pic de trafic. Versionnez chaque image Docker par commit, conservez les trois dernières versions déployables et documentez la procédure de retour arrière afin qu'un rollback reste une opération d'une commande, même en pleine soirée d'activité communautaire.

Guide 2 · Sécurité · Webhooks & API · ~510 mots

Sécurisation des webhooks et gestion des accès API

Les webhooks et les clés d'API sont les portes d'entrée les plus exposées d'une plateforme communautaire : ils reçoivent des appels depuis l'extérieur, souvent sans session utilisateur, et exécutent des effets de bord (publication de messages, déclenchement de modération, écritures en base). La règle fondamentale est de ne jamais faire confiance au réseau : chaque requête entrante doit être authentifiée, horodatée, limitée en débit et journalisée, même lorsqu'elle provient d'un partenaire connu.

Valider les payloads : signature, horodatage et schéma

Exigez une signature HMAC-SHA256 calculée sur le corps brut de la requête avec un secret partagé, transmise dans un en-tête dédié (par exemple X-Signature-256: sha256=…). Comparez les signatures en temps constant pour empêcher les attaques par canal temporel, et rejetez toute requête dont l'horodatage (X-Timestamp) s'écarte de plus de cinq minutes de l'horloge serveur afin de neutraliser les attaques par rejeu. Validez ensuite le JSON contre un schéma strict : types, longueurs maximales, énumérations fermées et refus des champs inconnus. Un payload qui échoue à la validation reçoit une erreur 400 générique, sans détail interne exploitable.

Mitigation des abus : quotas, allowlists et idempotence

Appliquez une limitation de débit par clé d'API et par adresse IP (par exemple 60 requêtes/minute avec file d'attente et en-têtes Retry-After), et durcissez les routes sensibles (envoi de messages, sanctions) avec des quotas séparés plus restrictifs. Lorsque l'émetteur dispose d'adresses IP stables, ajoutez une allowlist réseau en défense complémentaire — jamais en substitut de la signature. Rendez les opérations critiques idempotentes via une clé d'idempotence (Idempotency-Key) conservée 24 heures : toute répétition accidentelle ou malveillante retourne la réponse d'origine sans réexécuter l'effet de bord.

Secrets, en-têtes HTTP et rotation

Stockez les secrets de webhook et les clés d'API dans un gestionnaire de secrets ou, a minima, dans des variables d'environnement injectées au déploiement — jamais dans le dépôt ni dans les journaux. Attribuez à chaque intégration sa propre clé à périmètre restreint (lecture seule vs écriture, guildes autorisées) afin qu'une compromission reste circonscrite. Faites tourner les secrets au moins une fois par an et immédiatement après tout incident, en maintenant brièvement deux secrets actifs (primaire + précédent) pour une rotation sans interruption. Côté réponses, exposez des en-têtes de sécurité systématiques et des erreurs normalisées sans fuite d'implémentation :

// Middleware Express — vérification HMAC + fraîcheur + rate limit (extrait)
import crypto from "node:crypto";

const SECRET = process.env.WEBHOOK_SECRET;
const WINDOW_MS = 5 * 60 * 1000;

export function verifyWebhook(req, res, next) {
  const sig = req.headers["x-signature-256"];   // "sha256=<hex>"
  const ts = Number(req.headers["x-timestamp"]);
  if (!sig || !Number.isFinite(ts)) return res.status(401).json({ error: "unauthorized" });
  if (Math.abs(Date.now() - ts) > WINDOW_MS) return res.status(401).json({ error: "stale_request" });
  const expected = "sha256=" + crypto.createHmac("sha256", SECRET).update(req.rawBody).digest("hex");
  const a = Buffer.from(expected), b = Buffer.from(String(sig));
  if (a.length !== b.length || !crypto.timingSafeEqual(a, b)) {
    return res.status(401).json({ error: "unauthorized" });
  }
  next();
}
# En-têtes de réponse recommandés (Nginx ou middleware applicatif)
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
Journalisation : consignez l'identifiant de clé, la route, le code de statut et la latence — jamais le secret ni le corps complet. Corrélez ces journaux avec le dashboard de monitoring pour détecter les pics d'appels illégitimes avant qu'ils ne deviennent des incidents.

Réponse à incident et rotation des secrets

En cas de suspicion de compromission (pics d'appels anormaux, erreurs 401 massives suivies de succès, signalement d'un partenaire), révoquez immédiatement la clé concernée, générez-en une nouvelle à périmètre identique et diffusez-la par un canal sécurisé distinct du dépôt de code. Analysez ensuite les journaux sur une fenêtre de sept jours pour identifier les appels illégitimes et leurs effets, puis consignez l'incident : horodatage, clé concernée, requêtes incriminées, mesures correctives et date de rotation suivante. Cette discipline transforme chaque alerte en renforcement durable : règles de validation resserrées, quotas ajustés et périmètres de clés réduits au strict nécessaire.

Guide 3 · Infrastructure · Node.js & Next.js · ~530 mots

Bonnes pratiques d'infrastructure pour micro-services Node.js & Next.js

Exploiter plusieurs micro-services Node.js et une application Next.js en production exige une infrastructure prévisible : un point d'entrée unique qui termine TLS et répartit la charge, des politiques de cache explicites par type de contenu, des sondes de santé qui pilotent réellement le routage, et des sauvegardes dont la restauration est testée. L'objectif n'est pas la sophistication mais la reprise sur panne mesurée en minutes, avec des causes d'incident identifiables dans les journaux et les métriques.

Reverse proxy Nginx : TLS, routage et garde-fous

Placez Nginx en frontal : il termine TLS (configuration moderne, HSTS, redirections HTTP vers HTTPS), route par préfixe (/ vers Next.js, /api/ vers la passerelle, /healthz vers les sondes) et applique des garde-fous globaux — taille maximale de corps, timeouts amont, limitation de débit par IP et mise en tampon des réponses lentes. Activez la compression Brotli/Gzip uniquement pour les contenus textuels et excluez les flux déjà compressés. Chaque service amont déclare une sonde (GET /healthz répondant 200 en moins de 300 ms avec vérification base de données) ; tout amont en échec est temporairement exclu du pool, ce qui transforme un déploiement défectueux en dégradation partielle plutôt qu'en panne totale.

Stratégie de cache : distinguer le statique, le dynamique et l'API

Servez les assets Next.js compilés (/_next/static/) avec un cache long et immuable, les pages statiques avec revalidation courte, et ne mettez jamais en cache par défaut les réponses d'API authentifiées. Pour les endpoints publics coûteux (classements, statistiques), ajoutez un cache applicatif de courte durée (30 à 120 secondes) avec clé incluant la version et la langue, et exposez des en-têtes Cache-Control et ETag explicites. Invalidez par versionnage d'URL plutôt que par purge manuelle : c'est la seule stratégie qui reste fiable à 3 heures du matin pendant un incident.

Monitoring de latence et reprise sur panne

Mesurez la latence côté serveur par route (médiane p50, p95, p99) et côté client (Web Vitals pour Next.js : LCP, INP, CLS), avec des alertes sur le p95 et sur le taux d'erreur 5xx plutôt que sur des moyennes qui masquent les dégradations. Centralisez les journaux structurés (JSON avec requestId, route, statut, durée) et corrélez-les avec les métriques : un pic de p99 sans erreur applicative oriente vers la base ou le réseau, un pic d'erreurs 5xx vers un déploiement récent. Automatisez les sauvegardes quotidiennes de la base et des volumes persistants, chiffrez-les au repos, conservez-les hors site et — point critique — restaurez-les chaque trimestre sur un environnement isolé pour prouver qu'elles fonctionnent. Documentez enfin une procédure de reprise en une page : ordre de redémarrage des services, commandes de rollback, contacts d'astreinte et critères de fin d'incident.

# /etc/nginx/conf.d/platform.conf — frontal TLS + routage + garde-fous (extrait)
upstream nextjs { server 127.0.0.1:3000 max_fails=2 fail_timeout=15s; }
upstream gateway { server 127.0.0.1:4000 max_fails=2 fail_timeout=15s; }

server {
  listen 443 ssl http2;
  server_name lifestealmc.fr;

  client_max_body_size 2m;
  limit_req_zone $binary_remote_addr zone=api:10m rate=30r/s;

  location /_next/static/ {
    proxy_pass http://nextjs;
    proxy_cache_valid 200 30d;
    add_header Cache-Control "public, max-age=2592000, immutable" always;
  }
  location /api/ {
    limit_req zone=api burst=20 nodelay;
    proxy_pass http://gateway;
    proxy_read_timeout 15s;
    proxy_set_header X-Request-Id $request_id;
  }
  location = /healthz { proxy_pass http://gateway; access_log off; }
  location / { proxy_pass http://nextjs; }
}
# Sonde applicative minimale (Node.js) — binaire pour le proxy et l'orchestrateur
import http from "node:http";
import { checkDatabase } from "./db.js";

http.createServer(async (req, res) => {
  if (req.url !== "/healthz") { res.writeHead(404).end(); return; }
  const t0 = Date.now();
  try {
    await Promise.race([checkDatabase(), new Promise((_, r) => setTimeout(() => r(new Error("timeout")), 250))]);
    res.writeHead(200, { "content-type": "application/json" }).end(JSON.stringify({ ok: true, ms: Date.now() - t0 }));
  } catch { res.writeHead(503, { "content-type": "application/json" }).end(JSON.stringify({ ok: false })); }
}).listen(4000);
Objectifs de reprise : RTO inférieur à 15 minutes via redémarrage ordonné et rollback d'image versionnée ; RPO inférieur à 24 heures via sauvegardes quotidiennes testées. Chaque incident se conclut par un post-mortem d'une page : chronologie, cause racine, correctif et action préventive datée.
